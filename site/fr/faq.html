FAQ

FAQ Ritoko

Réponse courte

Ritoko enregistre des procédures navigateur, HTTP et MCP vérifiables et les rejoue avec un journal local. Ces réponses présentent l’installation, l’usage des modèles, les entrées tableur et les contrôles nécessaires pour reprendre des écritures incertaines.

Compatibilité et installation

Qu’est-ce que Ritoko ?＋

Ritoko enregistre une tâche résolue par un agent sous forme de workflow JSON réutilisable, puis l’exécute avec de nouveaux paramètres ou des lignes CSV/XLSX. Les étapes prises en charge incluent les actions navigateur, les requêtes HTTP et les outils MCP. Son journal local conserve le résultat de chaque ligne. Consultez le guide de démarrage.

Quand utiliser un workflow enregistré plutôt qu’un agent ?＋

Utilisez un workflow si la tâche est récurrente, ses entrées structurées et son résultat vérifiable. Faites appel à un agent si chaque exécution demande exploration ou jugement. L’agent peut découvrir une procédure que Ritoko reprend ensuite.

Que faut-il pour exécuter Ritoko ?＋

L’environnement local nécessite Node.js 24 ou une version ultérieure. Les workflows navigateur directs ont aussi besoin de Google Chrome ; les workflows HTTP/MCP autonomes peuvent s’exécuter sans navigateur. Ritoko est disponible en CLI, serveur MCP local via stdio et plugin Claude Code ou Codex.

Tous les clients MCP peuvent-ils se connecter à Ritoko ?＋

Un client local capable de lancer un processus stdio peut se connecter, dans les limites de ses propres fonctions. Claude Code et Codex CLI sont les clients testés avec le plugin. Un client cloud isolé ne peut pas accéder au processus ou aux fichiers locaux sans mécanisme de connexion distinct.

Ritoko peut-il utiliser mon navigateur déjà connecté ?＋

L’exécuteur direct peut se connecter à Chrome personnel avec votre autorisation de débogage distant, ou utiliser un profil isolé explicitement choisi. Connectez-vous et faites l’authentification multifacteur dans ce navigateur. La reprise navigateur en mode hôte demande l’autorisation d’exécuter des scripts dans la page ; l’évaluation actuelle de Codex en mode computer-use est en lecture seule et ne peut pas l’exécuter. Voir les choix du pilote.

Modèles et services

Ritoko reprend-il une tâche sans appeler de LLM ?＋

Son moteur de reprise directe n’effectue aucun appel LLM. L’enregistrement, la réparation et l’orchestration hôte peuvent utiliser le modèle de l’agent client. Un outil MCP, fournisseur OCR ou service de génération externe peut aussi utiliser des modèles et facturer ses appels. Voir les coûts des tâches récurrentes.

Faut-il une clé API LLM distincte ?＋

L’exécuteur direct n’en a pas besoin. Lors de l’enregistrement, de la réparation ou de l’orchestration hôte, l’agent client apporte le raisonnement via son abonnement ou sa configuration API. Les services externes nécessitent leurs propres accès configurés.

Ritoko fournit-il l’OCR ou un analyseur de factures ?＋

Non. L’outil facultatif document_image renvoie un JPEG/PNG téléchargé que le modèle de votre client peut lire. Un service OCR externe est une autre possibilité. Chaque nouveau document doit encore être interprété et vérifié avant que ses valeurs extraites soient soumises.

Puis-je planifier des exécutions récurrentes dans Ritoko ?＋

Ritoko n’intègre actuellement aucun planificateur. Un planificateur distinct peut lancer un workflow CLI existant. Prévoyez la connexion, les accès, les délais d’exécution et le suivi des éléments en revue avant un lancement sans surveillance ; consultez le rapport de chaque exécution.

Entrées et résultats

Quels formats de tableur Ritoko accepte-t-il ?＋

Il lit les fichiers .xlsx avec sélection d’une feuille, ainsi que les CSV séparés par des virgules ou points-virgules en UTF-8 ou Windows-1252. Les valeurs obligatoires et les clés métier vides ou dupliquées sont contrôlées avant le traitement. Voir la préparation des entrées.

Les lignes Excel masquées et les identifiants formatés sont-ils importés ?＋

Les lignes XLSX masquées ou filtrées sont également lues. Le format numérique Excel n’est pas appliqué : conservez au format Texte les identifiants ayant des zéros initiaux. Les formules utilisent leurs résultats enregistrés ; les erreurs ou résultats manquants des formules référencées sont traités comme des valeurs vides.

Modifier le fichier d’entrée change-t-il un lot repris ?＋

Non. Le lot utilise le workflow et les lignes figés dans son journal. Après avoir examiné les résultats précédents, lancez volontairement un nouveau lot pour des données corrigées ou nouvelles.

Que contient le rapport d’exécution ?＋

Le rapport JSON présente le statut du lot, les décomptes et résultats par ligne, les causes, messages et preuves ou fichiers disponibles. Il ne génère actuellement aucun rapport d’audit HTML ou CSV. Un résultat partiel demande encore une intervention ; le lot n’est pas terminé.

Écritures et reprise

Ritoko garantit-il l’absence de doublons dans les écritures ?＋

Non. En règle générale, il ignore les éléments confirmés et met en attente les écritures incertaines dans le journal de cette installation. Des clés métier, périmètres de destination, frontières commit et vérifications propres à chaque ligne corrects sont essentiels. Les soumissions indépendantes restent hors de ce journal. Voir la prévention des doublons à l’import.

Que signifie « en revue » après un plantage ou un délai dépassé ?＋

L’écriture a peut-être réussi sans confirmation exploitable. Vérifiez cet enregistrement précis dans la destination avant de le résoudre. Si le résultat n’est pas concluant, laissez-le en revue, y compris lors d’exécutions ultérieures. Voir la reprise d’une écriture incertaine.

Comment résoudre un élément en revue ?＋

Après vérification de la destination par une personne, résolvez-le en done si l’effet existe, ou en failed s’il n’a pas eu lieu. Une résolution en échec permet une soumission ultérieure. Dans les deux cas, ajoutez une note de preuve et confirmez explicitement la vérification ; les résolutions manuelles sont enregistrées comme décisions non vérifiées. Un agent doit obtenir la confirmation de l’utilisateur que la destination a été vérifiée.

Comment reprendre un lot interrompu ?＋

Utilisez run_resume ou la commande CLI ritoko resume pour un lot direct, et host_next pour un lot hôte. Les lignes confirmées le restent ; les échecs admissibles peuvent être réessayés ; les écritures incertaines restent bloquées. Résolvez le lot initial contenant l’incertitude avant un lot ultérieur bloqué par le doublon.

Que faire si la démonstration a déjà créé le premier enregistrement ?＋

Après avoir enregistré le workflow, utilisez run_adopt avec la ligne complète et exacte et une note de preuve. L’outil exécute les vérifications et journalise l’enregistrement déjà soumis pour que les reprises puissent l’ignorer. Ne soumettez pas à nouveau cette ligne tant que son résultat n’est pas réglé.

Ritoko peut-il vérifier la destination avant une écriture ou résoudre automatiquement un élément en revue ?＋

Le candidat Git 0.2.0 ajoute une recherche facultative ensure avant l’écriture et une recherche run_reconcile pour résoudre un résultat incertain ; npm 0.1.1 ne les inclut pas. Elles exigent un GET HTTP direct ou un outil MCP de lecture de confiance déclarant readOnlyHint: true, un périmètre explicite et des prédicats prouvant la présence ou l’absence. Une réconciliation non concluante ne modifie pas l’élément ; elle ne le soumet jamais à nouveau. Les vérifications navigateur, les exécutions hôte et les outils gérés par l’agent ne sont pas pris en charge ; la recherche doit figurer dans le lot figé. Voir la configuration et les limites.

Que se passe-t-il si un sélecteur enregistré change ?＋

Une exécution directe prise en charge peut se mettre en pause pour step_repair. Vérifiez qu’une nouvelle cible identifie le contrôle voulu ; le remplacement de la cible commit exige une confirmation explicite. Les échecs après soumission peuvent plutôt passer en revue. Le mode hôte ne propose actuellement aucune réparation de sélecteur. Voir l’enregistrement et la réparation des sélecteurs.

Puis-je répéter volontairement des lignes terminées ?＋

Oui, repeat: true ou l’option CLI --repeat relance les lignes terminées. Les éléments en revue restent bloqués. Utilisez cette option seulement si la répétition de l’effet métier est voulue.

Intégrations et données locales

Un enregistrement navigateur peut-il devenir automatiquement un workflow API ?＋

Non. La capture réseau facultative fournit des métadonnées fetch/XHR à des fins d’étude. Vérifiez le contrat API autorisé et l’authentification, testez une ligne et enregistrez explicitement les étapes HTTP prises en charge. Une écriture API incertaine ne doit pas entraîner automatiquement une autre soumission dans le navigateur.

Un workflow peut-il appeler un outil MCP existant ?＋

Oui, les serveurs configurés pris en charge peuvent fournir des étapes mcp, et les références hôte {ref: "agent"} réutilisent une connexion d’agent existante. Vérifiez les schémas, effets de bord, compatibilité du protocole et frais de service. Les appels d’outils ne sont pas réessayés automatiquement. Voir les choix d’intégration.

Où sont enregistrés les workflows, le journal et les fichiers de sortie ?＋

Par défaut, ils se trouvent sous ~/.ritoko ; RITOKO_HOME permet de modifier cet emplacement. Le journal contient les lignes métier et les valeurs enregistrées ordinaires. Les fichiers sauvegardés conservent leurs octets d’origine et peuvent contenir des données sensibles. Traitez les fichiers de l’installation comme des documents métier.

Comment stocker les identifiants d’accès ?＋

Déclarez des paramètres secrets alimentés par des variables d’environnement. Ne placez pas les identifiants dans le JSON du workflow ou les tableurs. Les identifiants d’exécution sont exclus du journal, mais les fichiers de réponses sauvegardés conservent leurs octets et demandent des précautions distinctes. Consultez la référence des intégrations.
